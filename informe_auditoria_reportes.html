01

Panorama general

Dos piezas independientes que se apoyan una en la otra: primero se registra lo que pasa, después se puede consultar.

El modelo de auditoría es la parte que escribe: cada vez que un SP de guardado (alta de perfil, edición de usuario, asociación de un permiso) confirma su transacción, deja una fila en una tabla central describiendo qué módulo, qué acción, quién y sobre qué registro.

El modelo de reportes es la parte que lee: una pantalla con un selector de reporte y filtros que arma una tabla temporal por cada tipo de consulta y se la entrega a un motor de grilla genérico (dbo.vct_RenderGrid) para que la muestre paginada, con buscador y exportables.

02

Modelo de auditoría

Una tabla, un SP de escritura, y un contrato simple para cualquiera que quiera loguear una acción nueva.

La tabla — dbo.M_AUDITORIA_ADMIN

Guarda un evento por fila. No hay estados ni versiones: es un log de solo-inserción (append-only).

Índices sobre (Modulo, Accion, Fecha DESC) y sobre UsuarioId, pensados para los filtros que arma la pantalla de Reportes.

El SP de logging — dbo.VCT_LOG_AUDITORIA

Es el único punto de entrada para escribir en la tabla. Cualquier SP de guardado lo invoca con un EXEC de una línea:

EXEC dbo.VCT_LOG_AUDITORIA
     @MODULO            = 'PERFILES',
     @ACCION            = 'ALTA',
     @USER_ID           = @IUSERID,
     @REGISTRO_AFECTADO = @VID_LOG,
     @DETALLE           = @VDETALLE_LOG;
Regla que rompió varios SPs en el camino: EXEC con parámetros nombrados solo acepta constantes o variables — nunca una expresión (CONVERT(...), 'texto ' + @var, UPPER(@x)). Todo valor calculado se resuelve primero en un SET @variable = … y recién ahí se pasa al EXEC.

El SP solo hace un INSERT; siempre se llama después del COMMIT TRANSACTION del guardado real, nunca antes — si el guardado falla y hace rollback, no queda un log fantasma de algo que no pasó.

Cómo instrumentar un ABM nuevo

Tres pasos, siempre en este orden dentro del SP de guardado:

  1. Determinar antes de escribir si es alta o edición (para loguear la acción correcta) — nunca inferirlo después del COMMIT.
  2. Ejecutar la transacción real (INSERT/UPDATE) y hacer COMMIT.
  3. Recién ahí, precomputar @VDETALLE_LOG y llamar a EXEC dbo.VCT_LOG_AUDITORIA.

Si el guardado es del tipo "insertar solo si no existe" (como las asociaciones de permiso o menú), loguear solo cuando la fila fue realmente nueva — un flag @VINSERTED BIT alcanza para no ensuciar el log con no-ops.

03

Modelo de reportes

Una pantalla, dos stored procedures por convención: uno arma el header y los filtros, el otro arma la grilla de resultados.

El catálogo — CAT_DATA

Qué reportes existen y en qué orden aparecen en el combo "Reporte" no está hardcodeado: sale de CAT_DATA filtrado por un PAR_KEY fijo.

SELECT CAT_DATA_CODE, CAT_DATA_DESC
FROM dbo.CAT_DATA
WHERE PAR_KEY = '11352CCA-DABB-40C1-9D55-DDA0F228CB23'

CAT_DATA_CODE es el id que viaja como ID_TASK_SEL en M_CONFIG y decide qué rama de los dos SPs de abajo se ejecuta.

Los dos SPs por pantalla

SPResponsabilidadDevuelve
M_CONFIG_PREV_REPORTESHeader del módulo, combo de Reporte, y los filtros propios de cada reporte (fecha, módulo, usuario, sector…)@PS_TITULO / @PS_FORMULARIO (HTML)
M_CONFIG_REPORTESLee los filtros ya guardados en M_CONFIG, arma un #TEMP con los datos, y llama al motor de grillaresultset (la grilla renderizada)

El primero se ejecuta al entrar o al cambiar de reporte/filtro; el segundo se dispara al togglear el reporte o apretar "Buscar" — ambos comparten el mismo PAR_KEY de sesión (M_CONFIG.PAR_KEY = @IPKEYJOB) para leer y persistir filtros.

El motor de grilla — dbo.vct_RenderGrid

En vez de armar HTML de tabla a mano (como hacía la versión vieja, con SELECT '<div>...' AS 'Columna'), cada reporte arma una tabla temporal con columnas en español como alias, y se la pasa al renderer genérico:

SELECT
    Usuario             = ISNULL(u.Id, ''),
    [Apellido y Nombre] = ISNULL(u.Name, ''),
    Estado              = ISNULL(cd.cat_data_desc, '')
INTO #TmpReporte2
FROM UsersSector US -- ...joins y filtros...

EXEC dbo.vct_RenderGrid
     @TempTableName = '#TmpReporte2',
     @FormId        = @FORM_ID,
     @ActionsJson   = '[]',   -- solo lectura, sin acciones de fila
     @PageSize      = 10,
     @HiddenColumns = '',
     @ScriptVersion = '16.0.0';

El nombre de cada columna del #TEMP es literalmente el título que aparece en el header de la grilla — no hay mapeo aparte que mantener.

Agregar un reporte nuevo

  1. CAT_DATA: insertar una fila con el próximo CAT_DATA_CODE y el nombre a mostrar (recordar que PKEY y CAT_INACTIVE son NOT NULL sin default).
  2. M_CONFIG_PREV_REPORTES: un IF (@Id_Reporte = 'N') nuevo que arma los campos de filtro específicos.
  3. M_CONFIG_REPORTES: el IF (@ID_REPORTE = 'N') correspondiente — arma el #TEMP y llama a vct_RenderGrid.

No hay today una tabla que declare "qué filtros usa cada reporte" — es información implícita en el código de ambos SPs. Con 4 reportes no pesa; si la lista crece bastante más, vale la pena versionarlo en una tabla de configuración.
