Modelo de Permisos: análisis y diseño

Separar autorización, navegación y representación de UI en tres contratos independientes — sin tablas nuevas, sin permisos por usuario, sin una segunda matriz de seguridad escondida en la capa de presentación.

Principio que no se negocia: GroupsActions + Actions es la única fuente de verdad de autorización. PrmActions describe cómo se ve una acción ya autorizada — nunca decide si está autorizada.

01

Diagrama lógico

Tres contratos, tres preguntas distintas. Ninguno reemplaza a otro.

Autorización

Users → GroupsUserMembers → Groups → GroupsActions → Actions

"¿Puede este usuario ejecutar esta operación?"

  • Única fuente de verdad de seguridad
  • Se valida siempre en el backend
  • 1 usuario = 1 grupo
Navegación

Groups → SidebarGroups → Sidebar

"¿Qué pantallas debería ver este grupo?"

  • Solo visibilidad/descubrimiento
  • Nunca se usa para autorizar
Representación UI

Actions → PrmActions (+ Sidebar)

"¿Cómo se ve una acción autorizada en esta pantalla?"

  • Botón, ícono, orden, destino
  • Depende de Actions, nunca al revés

La relación que faltaba nombrar explícitamente en tu esquema original: PrmActions.SideBarId → Sidebar.Id. Ya existe como columna en la tabla real — falta que sea una FK declarada, no solo una convención. Con eso, el diagrama que propusiste queda completo: no falta ninguna relación adicional, falta formalizar las tres que ya están implícitas.

03

Reglas de integridad recomendadas

Nada de esto agrega tablas — son constraints sobre lo que ya existe.

-- 1 usuario = 1 grupo, forzado en el motor, no solo en el SP de guardado
ALTER TABLE GroupsUserMembers
  ADD CONSTRAINT PK_GroupsUserMembers PRIMARY KEY (UserMemberId);
ALTER TABLE GroupsUserMembers
  ADD CONSTRAINT FK_GUM_Group FOREIGN KEY (GroupId) REFERENCES Groups(Id);

-- Un mismo permiso no se otorga dos veces al mismo grupo
-- YA EXISTE: PK_GroupsAction_GroupId_ActionId sobre (GroupId, ActionId) -- confirmado 13/9 con sp_help
ALTER TABLE GroupsActions
  ADD CONSTRAINT FK_GA_Action FOREIGN KEY (ActionId) REFERENCES Actions(Id);

-- PrmActions SIEMPRE describe una Action real, nunca una propia
ALTER TABLE PrmActions
  ADD CONSTRAINT FK_PRM_Action FOREIGN KEY (ActionID) REFERENCES Actions(Id),
  ADD CONSTRAINT FK_PRM_Sidebar FOREIGN KEY (SideBarId) REFERENCES Sidebar(Id),
  ADD CONSTRAINT UQ_PRM_Action UNIQUE (ActionID); -- ver decisión #2

-- Retirar una Action sin poder dejar huérfanos
ALTER TABLE Actions ADD IsActive BIT NOT NULL DEFAULT 1;

Sobre Actions.Id como clave natural (CLIENTES.CREATE): es válido mantenerla — es legible, estable y ya es el contrato que consume todo el sistema. Lo único que hay que proteger es que nunca se reutilice un código para significar otra cosa una vez publicado.

05

Diseño recomendado

Ninguna tabla nueva. El modelo que trajiste ya es correcto conceptualmente — lo que falta es declarar en el motor lo que hoy es solo convención de código:

  1. Confirmar el nombre real de columna en GroupsActions — hecho: es ActionId, y la PK compuesta ya existe en producción.
  2. Agregar las FKs que faltan (sección 3): GroupsUserMembers→Groups, GroupsActions→Actions, PrmActions→Actions y PrmActions→Sidebar — antes, limpiar duplicados si los hubiera.
  3. Agregar Actions.IsActive para poder "apagar" sin borrar.
  4. Nada de tabla nueva para representar la relación Action↔PrmActions↔Sidebar: ya existen las tres columnas, solo faltaba la FK.
06

Flujo de autorización para una llamada backend

  1. El backend recibe la request con el usuario autenticado y el código de acción solicitado (ej. CLIENTES.CREATE).
  2. Resuelve el grupo: SELECT GroupId FROM GroupsUserMembers WHERE UserMemberId = @UserId — con la PK de la sección 3, esto devuelve como máximo una fila por construcción.
  3. Verifica el permiso: SELECT 1 FROM GroupsActions WHERE GroupId=@GroupId AND ActionId=@ActionCode.
  4. Si no existe → rechaza, sin importar qué haya mostrado el frontend.
  5. Si existe → ejecuta la operación real.

PrmActions y SidebarGroups no participan en este flujo. Ni se consultan para decidir si la operación procede.

07

Flujo de construcción de una pantalla y sus botones

  1. Al entrar a la app, se resuelve el GroupId del usuario (una sola vez).
  2. Para armar el menú: Sidebar ⋈ SidebarGroups WHERE GroupId=@GroupId — solo navegación.
  3. Dentro de una pantalla ligada a un SideBarId, para saber qué botones pintar: PrmActions WHERE SideBarId=@SideBarId AND EXISTS (GroupsActions WHERE GroupId=@GroupId AND ActionId=PrmActions.ActionID).
  4. El botón se pinta solo si esa intersección existe — pero el ícono, el orden y el destino salen de PrmActions, nunca la decisión de mostrarlo o no.
  5. Al hacer clic, se dispara la operación real, que vuelve a pasar por el flujo de la sección 6 en el backend — el filtrado de UI nunca es la única barrera.
08

Estrategia para tablas sin ABM

No hace falta ABM para Actions/PrmActions/Sidebar si el costo de construirlo no se justifica — pero el cambio tiene que dejar de ser un INSERT suelto en producción.

  • Carpeta versionada en el repo (ej. /db/seed/), un script por feature, nunca editado in situ en un ambiente.
  • Cada script es idempotente: IF NOT EXISTS (...) INSERT o MERGE, nunca un INSERT crudo que falle o duplique en la segunda corrida.
  • Nunca DELETE físico de una Action en uso — solo IsActive = 0.
  • El script se commitea en el mismo PR que la funcionalidad que lo necesita — el historial de Git es el historial del catálogo.
  • Mismo criterio para CAT_DATA — el seed de Reportes que corrimos hoy a mano debería vivir como script versionado, no solo en esta conversación.

10

Decisiones a cerrar (Martín / Esteban)

  1. ¿Puede una misma Action tener más de una representación en PrmActions (aparecer en dos pantallas distintas)? Define si el UNIQUE es sobre ActionID solo o sobre (ActionID, SideBarId).
  2. ¿Se agrega ya el UNIQUE/PK en GroupsUserMembers.UserMemberId? Requiere primero verificar que no haya usuarios con más de un grupo cargado hoy.
  3. Política de retiro de Actions: ¿siempre IsActive=0, o se permite borrar cuando no tiene GroupsActions asociados?
  4. ¿Quién escribe los scripts de seed cuando se agrega una pantalla nueva — quien programa la feature, o un rol de administración de sistema?
  5. ¿Vale una tabla liviana de control (script ejecutado / ambiente / fecha) para trackear los seeds, o alcanza con disciplina manual?
  6. ¿Se cachea GroupsActions en el backend? Si sí, qué evento invalida el caché — cambios en GroupsActions, en GroupsUserMembers, o ambos.
  7. Para la futura API independiente de Mühle: ¿revalida contra la base en cada request, o resuelve un claim/token precomputado? Si es lo segundo, definir TTL y refresh.
